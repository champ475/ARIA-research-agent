# Load run, 17 Oct 2026 (a laptop, one process)

Measured with `python loadtests/run.py` against the fake LLM (400 ms per call, 600 ms to the first streamed token) and fake market data (150 ms per call), on a Windows laptop where Locust, the app (one process) and Postgres (Docker) share the same CPU. The app was CPU-bound: its one process used about 90% of a core. The targets are the PRD's. The single-user baseline is measured on the same server just before, after a 20 s warm-up. This is a snapshot of one machine; the per-release report comes from `.github/workflows/loadtest.yml`.

## Clean run: does it meet the targets?

20 concurrent users for 240 s, 60% equity, 15% fund, 10% screener, 10% alerts, 5% report.

| Target | Measured | Result |
|---|---|---|
| turn error rate < 1% | 0.00% (0/582) | PASS |
| equity TTFT p50 <= 6 s | 4.60 s | PASS |
| equity TTFT p95 <= 15 s | 6.20 s | PASS |
| report turn p95 <= 60 s | 6.20 s | PASS |
| concurrent equity TTFT p95 within 1.5x single-user | 1.88x (6.20 s vs 3.30 s) | **FAIL** |
| memory flat over the soak | not assessed: run was 4 min; a soak verdict needs 30+ | n/a |
| server CPU (informational; 100 = one core) | mean 88, peak 98 | n/a |

| Kind | Turns | Failures | TTFT p50 | TTFT p95 | Turn p95 |
|---|---|---|---|---|---|
| alerts | 71 | 0 | 3.60 s | 4.60 s | 4.90 s |
| equity | 351 | 0 | 4.60 s | 6.20 s | 7.60 s |
| mf | 88 | 0 | 3.50 s | 4.40 s | 4.70 s |
| report | 19 | 0 | 3.80 s | 5.80 s | 6.20 s |
| screener | 53 | 0 | 3.70 s | 5.10 s | 5.30 s |

**Reading it.** Every latency target holds except the concurrency ratio: 20 users see an equity p95 of 6.2 s against 3.3 s for one user (1.88x; the target is 1.5x). The CPU line says why: one Python process runs out of core at about 2.4 turns a second. Two ways to close it: run more replicas (the app keeps no per-process state that matters: `docker compose up --scale app=2`), or cut CPU per turn further.

The first load run found the biggest single cost: plotly building the candlestick chart was about two thirds of a turn's CPU. It is now cached per price history (`graph/nodes/communication_layer.py::_chart_json`). With that change the same profile went from equity p95 9.8 s to 6.2 s, and from about 1.5 to 2.4 turns a second.

## Chaos run: do faults hurt, and does it recover?

20 concurrent users for 220 s, with a fault every 45 s.

| Target | Measured | Result |
|---|---|---|
| server ready again within 60 s after every injected fault | 4/4 recovered in time | PASS |
| turn failures while faults were on (informational) | 2.96% (13/439) | n/a |
| answers that named missing data (informational) | 0 of 439 turns | n/a |
| latency targets | not judged: faults were injected in this run | n/a |

| At (s) | Scenario | Event | Server ready again after |
|---|---|---|---|
| 40.0 | slow_llm | start | - |
| 65.1 | slow_llm | end | 0.1 s |
| 85.0 | flaky_llm | start | - |
| 110.3 | flaky_llm | end | 0.3 s |
| 130.0 | upstream_500 | start | - |
| 155.3 | upstream_500 | end | 0.3 s |
| 175.0 | db_restart | start | - |
| 176.4 | db_restart | restarted | 0.7 s |

**Reading it.** The server was ready again within a second of every fault, including a Postgres restart under load. While 30% of LLM calls failed, the client retried, and 13 of 439 turns (3%) still ended in the "shared AI service isn't available" message; the rest answered. Latency during faults is shown but not judged.
